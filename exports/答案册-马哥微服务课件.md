# 马哥微服务课件 —— 答案与解析

> 共 99 题，编号与《试题册-马哥微服务课件.md》一致。


## 微服务笔试

### 1. 【架构演变】SOA（面向服务的架构）中，用于将一系列不同的应用程序集成到单个基础架构、但属于重量级产品且成本很高的通信基础设施是？

**答案**

**B**　ESB 企业服务总线

**解析**

SOA 各服务之间通过 ESB（Enterprise Service Bus，企业服务总线）通信，ESB 由大量规则和原则集成，缺少好的开源方案、只能使用商业产品，因此成本高、部署笨重，其单点依赖与费用问题反而成为所有服务的瓶颈。【衍生知识点】SOA 特点是降低服务耦合度、有利于升级扩展，但服务相互访问复杂。

---

### 2. 【架构演变】关于微服务与 SOA 的关系，下列说法正确的是？

**答案**

**B**　微服务属于 SOA 的子集，SOA 可看作面向服务的 1.0 版本，微服务是 2.0 版本

**解析**

课件明确指出：微服务属于 SOA 的子集，SOA 可以认为面向服务的 1.0 版本，微服务可以认为面向服务的 2.0 版本。【衍生知识点】微服务“分而治之”，按业务拆分成多个可独立开发、部署、维护的服务，服务间采用轻量级标准通信机制（通常是基于 HTTP 的 RESTful API）。

---

### 3. 【架构对比】下列哪一项不属于单体（巨石）架构的缺点？

**答案**

**C**　可按功能模块进行垂直扩展，扩缩容非常灵活

**解析**

单体的缺点包括复杂性高、可靠性差、交付效率低、伸缩性差——单体只能按整体横向扩展，无法分模块垂直扩展，因此 C 说法错误。【衍生知识点】单体总结：架构简单、部署方便，但打包编译部署升级效率低下、各功能耦合度高、扩展困难、扩缩容不灵活，适合小型简单项目。

---

### 4. 【服务网格】被称为“后微服务时代”标志、采用边车代理（Sidecar Proxy）模式接管应用所有对外通信的架构是？

**答案**

**B**　服务网格 Service Mesh

**解析**

为解决 Spring Cloud 方案偏重、与业务无关的功能实现成本高的问题，虚拟化基础设施引入“服务网格”（Service Mesh）的“边车代理模式”（Sidecar Proxy），由系统自动在服务容器（通常是 K8s 的 Pod）中注入通信代理服务器。【衍生知识点】代理除实现服务间通信（数据平面通信）外，还接收控制器指令（控制平面通信），实现熔断、认证、度量、监控、负载均衡等附加功能，对应用透明、无需改动业务代码。

---

### 5. 【Serverless】无服务架构（Serverless）主要涉及哪两块内容？

**答案**

**B**　后端设施（BaaS）与函数（FaaS）

**解析**

无服务只涉及两块内容：后端设施（数据库、消息队列、日志、存储等，运行在云中，称 BaaS，Backend as a Service）和函数（业务逻辑代码，运行在云端，称 FaaS，Function as a Service）。【衍生知识点】无服务天生“无限算力”的假设决定了它必须按使用量计费，函数不会常驻，因此存在冷启动时间，不适合有复杂业务逻辑、依赖服务端状态、响应速度要求高的应用。

---

### 6. 【架构选型】软件大师 Martin Fowler 在 2015 年提出、且已被业界普遍公认为务实选择的架构策略是？

**答案**

**B**　单体优先（Monolith First）

**解析**

Martin Fowler 发现几乎所有成功的微服务故事都从一个变得太大而被分解的单体开始；几乎所有从头构建为微服务系统的系统都以严重麻烦告终。因此他提出“单体优先”（Monolith First）。【衍生知识点】单体优先四种策略：模块化单体、边缘剥离、整体替换、粗粒度服务。在人数不多、资金不充裕、需要快速推向市场的团队，建议使用“单体优先”。

---

### 7. 【Spring Cloud】Spring Cloud 本质是在哪个框架的基础上，增加一堆微服务相关规范并对应用上下文（Application Context）进行功能增强？

**答案**

**B**　Spring Boot

**解析**

Spring Cloud 的本质是在 Spring Boot 的基础上增加微服务相关规范，并对应用上下文进行功能增强；既然 Spring Cloud 是规范就需要去实现，目前已有 Spring 官方、Spring Cloud Netflix、Spring Cloud Alibaba 等实现。【衍生知识点】Spring Boot 提供自动配置、起步依赖、嵌入式服务器（Tomcat/Jetty/Undertow）、Actuator 监控等开箱即用能力，是构建独立自包含应用的基础。

---

### 8. 【微服务框架】在 Spring Cloud Alibaba 组件中，同时提供服务注册与配置中心能力的是？

**答案**

**C**　Nacos

**解析**

Spring Cloud Alibaba 的组件中 Nacos 提供“服务注册和配置中心”能力；Eureka 仅聚焦服务注册与发现且已停更，Consul 是 Spring Cloud 原生体系的服务注册中心。Nacos 与 RocketMQ 已逐渐成为国内分布式注册配置中心和分布式消息的事实标准。【衍生知识点】Spring Cloud Alibaba 其他组件：Sentinel（客户端容错保护）、Dubbo（远程调用）、Seata（分布式事务）、RocketMQ（消息队列）。

### 9. 【ZooKeeper 由来】ZooKeeper 最初由哪家公司开发，用于解决分布式协调与分布式单点问题？

**答案**

**B**　Yahoo（雅虎研究院）

**解析**

ZooKeeper 最早起源于雅虎研究院的一个研究小组，开发人员试图开发一个通用的无单点问题的分布式协调框架。因内部很多项目以动物命名（如著名的 Pig 项目），首席科学家一句“就变成动物园了”促成了“动物园管理员”这个名字。【衍生知识点】后来 Apache ZooKeeper 成为 Hadoop、HBase 等分布式框架使用的有组织服务的标准。

---

### 10. 【ZooKeeper 数据模型】ZooKeeper 内部维护的数据模型是哪种结构？

**答案**

**B**　与 Linux 文件系统类似的树状（层次）结构

**解析**

ZooKeeper 内部维护了一个层次关系（树状结构）的数据模型，表现形式类似于 Linux 的文件系统，甚至连操作的种类都一致；由斜杠（/）分割的路径就是一个 ZNode，每个 ZNode 保存自己的数据内容和一系列属性信息。【衍生知识点】ZooKeeper 中的节点分两类：构成集群的主机节点，以及内存数据模型中的数据单元 ZNode。

---

### 11. 【ZooKeeper 功能】ZooKeeper 实现配置中心时采用的变更通知方式是？

**答案**

**C**　推拉结合：客户端注册关注节点，数据变更时服务端发 Watcher 事件通知，客户端再主动拉取最新数据

**解析**

ZooKeeper 采用的是推拉相结合的方式：客户端向服务端注册自己需要关注的节点，一旦该节点数据发生变更，服务端就会向相应客户端发送 Watcher 事件通知，客户端收到通知后需主动到服务端获取最新数据。【衍生知识点】Watcher（事件监听器）是 ZooKeeper 实现分布式协调服务的重要特性；此外临时节点在客户端与服务器会话失效时会被自动清除。

---

### 12. 【ZooKeeper 命令】在 zkCli 中创建临时节点（退出即丢失）应使用的命令是？

**答案**

**B**　create -e /path data

**解析**

默认创建的是持久节点，即退出不丢失；create -e 可以创建临时节点（退出就丢失）。另外只有持久节点才支持创建子节点，临时节点不支持，且不能递归创建子节点。【衍生知识点】delete 用于删除不包含子节点的节点（相当于 rmdir），deleteall /path 可删除所有节点内数据（相当于 rm -rf）。

---

### 13. 【ZooKeeper 集群角色】ZooKeeper 集群中负责处理写请求、是事务请求唯一调度和处理者、并负责投票发起与决议的节点是？

**答案**

**C**　Leader（领导者）

**解析**

领导者（Leader）负责处理写入请求，是事务请求的唯一调度和处理者，负责进行投票发起和决议并更新系统状态。跟随者（Follower）接收客户请求并向客户端返回结果，在选举 Leader 过程中参与投票。【衍生知识点】观察者（Observer）转交客户端写请求给 Leader 并同步 Leader 状态；学习者（Learner）是和 Leader 进行状态同步的节点统称，包括 Follower 和 Observer。

---

### 14. 【ZooKeeper 集群角色】Observer（观察者）与 Follower（跟随者）的唯一区别是？

**答案**

**B**　Observer 不参与 Leader 投票，也不参与写操作的“过半写成功”策略

**解析**

Observer 会转交客户端写请求给 Leader 节点，并同步 Leader 状态，其与 Follower 唯一区别就是不参与 Leader 投票，也不参与写操作的“过半写成功”策略。【衍生知识点】在节点数很多、读多写少的场景下增加 Observer，可以在不降低写性能（不增加投票成本）的前提下提升读吞吐。

---

### 15. 【ZooKeeper 选举】ZooKeeper 集群选举 Leader 时对比投票信息的规则是？

**答案**

**C**　优先比较 ZXID，ZXID 大者为 Leader；若 ZXID 相同则比较 myid，myid 大者为 Leader

**解析**

对比投票时优先检查 zxid，如果 zxid 不一样则 zxid 大的为 Leader；如果 zxid 相同则继续对比 myid，myid 大的一方为 Leader。成为 Leader 的必要条件是具有最高的 zxid，且至少 n/2+1 个节点响应。【衍生知识点】节点角色状态有 LOOKING（寻找 Leader）、LEADING、FOLLOWING、OBSERVER 四种。

---

### 16. 【ZooKeeper 端口】ZooKeeper 集群配置项 server.1=10.0.0.101:2888:3888 中，2888 端口的作用是？

**答案**

**B**　Leader 与 Follower 之间的数据同步端口

**解析**

格式为 server.MyID=服务器IP:Leader和Follower的数据同步端口(只有 Leader 才会打开):Leader和Follower选举端口(Leader 和 Follower 都有)，因此 2888 是数据同步端口，3888 是选举端口。【衍生知识点】客户端连接端口由 clientPort 指定，默认 2181；验证方式：follower 会监听 3888/tcp，只有 leader 监听 2888/tcp。

---

### 17. 【ZooKeeper 协议】ZooKeeper 主要依赖哪个协议实现分布式数据一致性，且该协议是专门为其设计的支持崩溃恢复的原子广播协议？

**答案**

**C**　ZAB（ZooKeeper Atomic Broadcast）

**解析**

在 ZooKeeper 中主要依赖 ZAB 协议实现分布式数据一致性，基于该协议 ZooKeeper 实现了一种主备模式的系统架构来保持集群中各副本之间的数据一致性；它主要用在主-备模式的系统中。【衍生知识点】ZAB 恢复模式流程：Leader Election（选举阶段）→ Discovery（发现阶段）→ Synchronization（同步阶段）→ Broadcast（广播阶段）。Paxos 由 Leslie Lamport 于 1990 年提出；Raft 由 Diego Ongaro 和 John Ousterhout 于 2013 年提出，被 kafka、etcd、nacos、Consul 采用。

---

### 18. 【ZooKeeper 集群特性】关于 ZooKeeper 集群可用性，下列说法正确的是？

**答案**

**C**　整个集群中只要有超过集群数量一半的 ZooKeeper 正常工作，整个集群对外就是可用的

**解析**

整个集群中只要有超过集群数量一半的 ZooKeeper 正常工作，整个集群对外就是可用的。2 台组集群时任意一台宕机即不可用；3 台时损坏一台仍可用、再损坏一台不可用；4 台损坏两台也只剩两台（不大于一半）同样不可用，因此 3 台与 4 台容错能力相同。【衍生知识点】因为只要 >n/2 台可用系统即保持可用，所以 ZooKeeper 集群通常由奇数台 Server 节点组成。

---

### 19. 【ZooKeeper 监控】按课件配置开启 Prometheus 监控后，ZooKeeper metrics 默认监听的端口是？

**答案**

**B**　7000

**解析**

在 zoo.cfg 中配置 metricsProvider.className=org.apache.zookeeper.metrics.prometheus.PrometheusMetricsProvider、metricsProvider.httpPort=7000，即可通过 curl 127.0.0.1:7000/metrics 获取指标。【衍生知识点】该配置需 stop 再 start，restart 可能会失败；ZooKeeper 安装目录默认为 /usr/local/zookeeper，tickTime=2000、initLimit=10、syncLimit=5。

### 20. 【ZooKeeper 运维】测试 ZooKeeper 服务是否启动、若回复 imok 表示已启动的四字命令是？

**答案**

**B**　ruok

**解析**

ruok 用于测试是否启动了该 Server，若回复 imok 表示已经启动；stat 查看哪个节点被选为 Follower 或 Leader；conf 输出相关服务配置的详细信息；mntr 输出一些运行时信息。【衍生知识点】默认情况下这些四字命令可能被拒绝（提示 xxxx is not executed because it is not in the whitelist），需在 zoo.cfg 中添加 4lw.commands.whitelist=* 放开，生产中建议只放开 conf,stat,ruok,isro 等安全命令。

### 21. 【消息队列】2006 年发布、跨语言跨平台并真正促进消息队列繁荣发展的消息协议规范是？

**答案**

**B**　AMQP（高级消息队列协议）

**解析**

2001 年 SUN 发布 JMS 规范，但它只适用于 Java 语言、与语言绑定，没有从根本上解决问题；2006 年 AMQP（Advanced Message Queuing Protocol）规范发布，跨语言跨平台，真正促进了消息队列的繁荣发展。【衍生知识点】2007 年 Rabbit 技术公司基于 Erlang 语言开发了符合 AMQP 规范的 RabbitMQ 1.0；1983 年世界上第一个消息队列软件 TIB 实现了发布订阅（Publish/Subscribe）模型。

---

### 22. 【消息队列】电商秒杀、抢红包等大型活动中，消息队列“削峰填谷”主要解决的是什么问题？

**答案**

**B**　瞬时流量脉冲导致系统超负荷甚至崩溃，或过度限流导致大量请求失败

**解析**

秒杀等大型活动会带来较高的流量脉冲，或因没做保护而系统超负荷甚至崩溃，或因限制太过导致请求大量失败，消息队列可提供削峰填谷的服务来解决。MQ 的主要应用场景还包括异步解耦、顺序收发、分布式事务一致性、大数据分析、分布式缓存同步、蓄流压测。【衍生知识点】消息队列是一种异步的服务间通信方式，消息在被处理和删除之前一直存储在队列上，每条消息仅可被一位用户处理一次。

### 23. 【Kafka 概念】Kafka 中消息的分类单位是？

**答案**

**B**　Topic 主题

**解析**

Topic 是消息的主题，可以理解为消息的分类：一个 Topic 相当于数据库中的一张表，一条消息相当于关系数据库的一条记录；物理上不同 Topic 的消息分开存储在不同的文件夹，用户只需指定 Topic 即可生产或消费数据。【衍生知识点】Broker 是 Kafka 实例，每个 Broker 都有集群内不重复的编号（broker-0、broker-1……）；Consumer Group 中同一 Topic 的一条消息只能被同组内一个 Consumer 消费。

---

### 24. 【Kafka 概念】Kafka 中每个 Topic 在物理上被切分为多份，每一份称为？

**答案**

**B**　Partition（分区）

**解析**

Partition 是物理上的概念，每个 Topic 分割为一个或多个 Partition，其表现形式就是一个一个的文件夹，文件夹下存储该 Partition 的数据和索引文件；分区可实现负载均衡、提高 Kafka 吞吐量。【衍生知识点】一般 Partition 数不要超过节点数；同一个 Topic 在不同分区的数据是不重复的；同一个 Partition 数据是有顺序的，但不同 Partition 之间无序。

---

### 25. 【Kafka 概念】关于 Kafka 消息顺序性，下列说法正确的是？

**答案**

**B**　Kafka 保证一个 Partition 内消息有序，分区之间数据是无序的

**解析**

Kafka 保证一个 Partition 内的消息的有序性，分区间数据是无序的；如果对数据的顺序有要求，应在创建主题时将分区数 partitions 设置为 1。【衍生知识点】Kafka 通过 O(1) 的磁盘数据结构提供消息持久化，即使数以 TB 级别的消息存储也能保持长时间稳定性能。

---

### 26. 【Kafka 副本】关于 Kafka 中 AR、ISR、OSR 的关系，正确的是？

**答案**

**A**　AR = ISR + OSR

**解析**

AR（Assigned Replicas）是分区中所有副本的统称（含 leader 和 follower）；ISR（In Sync Replicas）是与 leader 保持同步的副本集合（含 leader 本身），是 AR 的子集；OSR（Out-of-Sync Replicas）是同步滞后的 follower 集合，也是 AR 的子集。因此 AR = ISR + OSR。【衍生知识点】副本数不能超过集群节点的数量，基本于数据安全建议至少 2 个。

---

### 27. 【Kafka 副本】Kafka 的副本数（leader+follower）与 Elasticsearch 的副本数，主要区别是？

**答案**

**B**　Kafka 的副本数包括主分片数，而 Elasticsearch 的副本数（follower）不包括主分片数

**解析**

课件明确指出：Kafka 中的副本（leader+follower）数包括主分片数，而 Elasticsearch 中的副本数（follower）不包括主分片数。【衍生知识点】Kafka 分区每个都有一个 Broker 作为 Leader、一个 Broker 作为 Follower，类似于 ES 中的主分片和副本分片；副本数不能超过集群节点数量。

---

### 28. 【Kafka 可靠性】要实现 Kafka 强一致性，需将 min.insync.replicas 设置为大于 1，并将 acks 设置为？

**答案**

**C**　all 或 -1

**解析**

要实现强一致性，需要将 min.insync.replicas 参数设置为大于 1，确保至少有 N 个副本确认数据写入才认为写操作成功，并且需要设置 acks 为 all 或 -1，表示 Leader 需等待所有 ISR 确认接收到消息后才向生产者返回 ack。【衍生知识点】Kafka 可以配置为提供强一致性，但这是以牺牲一定的性能为代价的，实际使用需在一致性与性能之间权衡。

---

### 29. 【Kafka 复制配置】Kafka 中 acks=0 的语义是？

**答案**

**A**　生产者发送消息后不等确认即认为成功

**解析**

acks=0：生产者发送消息后不等确认即认为成功，相当于没有复制，只有单个副本存储在 Leader 上；acks=1：消息发送到 Leader 即认为成功，相当于异步复制；acks=all：需要等待 ISR 列表中所有同步的 Slave 都确认才认为成功，相当于同步复制。【衍生知识点】Kafka 允许 Leader 在数据还未被所有 Follower 复制之前就将写操作确认为成功，这也带来了 Leader 故障时新数据可能丢失的一致性问题。

### 47. 【Sentinel 原理】Sentinel 底层采用哪种高性能的滑动窗口数据结构来统计实时秒级指标数据，以支撑写多于读的高并发场景？

### 48. 【Sentinel 对比】Sentinel 与 Hystrix 在隔离策略上的区别是？

**答案**

**B**　Sentinel 通过限制资源并发线程数进行隔离，Hystrix 通过线程池进行隔离

**解析**

Hystrix 通过线程池的方式对依赖资源进行隔离，好处是资源和资源之间最彻底隔离，缺点是增加了线程切换成本、需要预先给各个资源分配线程池大小。Sentinel 通过限制资源并发线程的数量来减少不稳定资源对其它资源的影响，没有线程切换损耗，也不需要预先分配线程池大小。【衍生知识点】Sentinel 还支持集群流控、流量整形（预热模式与匀速排队）、系统自适应保护、热点识别/防护，这些 Hystrix 均不支持；Sentinel 提供开箱即用的控制台，Hystrix 仅简单监控查看。

### 50. 【Seata 角色】Seata 中负责维护所有全局和分支事务的状态、驱动全局提交或回滚的角色是？

### 51. 【Seata 模式】Seata 的默认事务模式，且业务无侵入的是？

### 52. 【Seata 模式】需要业务方自行编写 Try、Confirm、Cancel 三个接口的侵入式分布式事务模式是？

**答案**

**C**　TCC 模式

**解析**

TCC 即 Try 尝试、Confirm 确认、Cancel 取消，三个方法均由业务编码实现，因此 TCC 可被称为服务化的资源管理器：Try 负责资源的检查和预留，Confirm 执行真正的业务，Cancel 执行预留资源的取消。TCC 的性能最强（无需生成快照、无需全局锁），但实现复杂、需做好幂等处理。【衍生知识点】TCC 不依赖底层数据库事务，而是依赖补偿操作，可实现跨数据库、跨应用资源管理，适用于核心系统等对性能要求很高的场景。

### 53. 【Seata 模式】Seata 中基于数据库 XA 协议、以 CP 强一致性工作，但 prepare 后分支事务需阻塞等待、锁定周期长性能差的模式是？

**答案**

**A**　XA 模式

**解析**

XA 模式基于数据库的 XA 协议来实现 2PC，以 CP 模式工作、强一致；其优势是业务无侵入、数据库支持广泛，缺点是 XA prepare 后分支事务进入阻塞阶段，收到 commit 或 rollback 前必须阻塞等待，事务资源长时间得不到释放、锁定周期长、应用层无法干预、性能差。【衍生知识点】XA 适用于想迁移到 Seata 平台基于 XA 协议的老应用，以及金融行业并发量不大但数据很重要的场景；使用上与 AT 模式唯一区别是数据源代理用 DataSourceProxyXA 替代 DataSourceProxy。

### 54. 【Seata 实现】AT 模式实现数据回滚所依赖的机制是？

**答案**

**B**　生成反向 SQL 并依赖数据库额外附加的 undo_log 表记录数据快照

**解析**

AT 模式是阿里 SEATA 独有模式，通过生成反向 SQL 实现数据回滚，需要在数据库额外附加 UNDO_LOG 表。第一阶段 RM 注册分支事务、记录 undo-log（数据快照）、执行业务 SQL 并提交、报告事务状态；第二阶段提交时删除 undo-log，回滚时根据 undo-log 恢复数据到更新前。【衍生知识点】AT 与 XA 的主要区别：XA 第一阶段不提交事务、锁定资源，AT 第一阶段直接提交、不锁定资源；XA 依赖数据库机制回滚，AT 利用数据快照回滚。

### 57. 【网关概念】Spring Cloud Gateway 中一个 Route（路由）包含哪些组成部分？

一个 Route 包含：Route ID（自定义、路由唯一标识）、predicates（路由断言，判断请求是否匹配和符合转发规则）、URI（路由目的地，支持 lb、http、websocket 等）、filters（路由过滤器，对请求或响应过滤处理，为可选项）。【衍生知识点】URI 有三种配置方式：websocket 配置（ws://）、http 地址配置（http://）、注册中心配置（lb://服务名，lb 表示负载均衡）。

### 58. 【网关过滤器】Spring Cloud Gateway 中 StripPrefix=1 的作用是？

**答案**

**解析**

### 59. 【网关过滤器】Spring Cloud Gateway 中，当路由过滤器、DefaultFilter 和 GlobalFilter 的 order 值相同时，执行顺序是？

**答案**

**B**　DefaultFilter > 路由过滤器 > GlobalFilter

**解析**

## 微服务面试

### 78. 【面试·架构】简述单体架构与微服务架构的优缺点，并说明为什么 Martin Fowler 提出并推崇“单体优先”。

**答案**

一、单体（巨石）架构：一个项目一个工程，统一部署、一个进程，Java 中常打成 jar/war。优点是架构简单、易于开发和测试、部署方便，扩展时把 war 复制多份放到多台服务器做负载均衡即可。缺点是：①复杂性高，多模块耦合、代码结构混乱、重复代码多、难以修改和重构；②可靠性差，某个功能模块出问题可能引起整个应用崩溃，改 Bug 或升级某模块都要停掉整个服务、整体重新打包部署；③交付效率低，构建部署耗时长、编译耗时长；④伸缩性差，只能按整体横向扩展，无法分模块垂直扩展。
二、微服务架构：按业务把大型系统拆分成多个可独立开发、部署和维护的微服务，每个服务只做一件事、单一职责，服务间采用轻量级标准通信机制（通常是基于 HTTP 的 RESTful API），各服务可以有独立数据库。优点是：每个服务足够内聚、易理解维护，可由 2~5 人小团队独立开发；灵活部署、独立扩展；去中心化治理，各组件可针对业务特点选择不同技术平台；局部修改容易部署；易与第三方集成（Jenkins、Hudson、Bamboo 等持续集成）；资源有效隔离（每个微服务拥有独立数据源）。缺点是：把项目拆成多个独立工程，增加了开发、测试、运维、监控复杂度；需保证不同服务间数据一致性，引入分布式事务与异步补偿机制；需快速检测故障源并自动恢复，要实现监控和日志记录；对开发和运维的技术能力要求更高；只适用于复杂大系统，小型应用盲目拆分只会增加维护和开发成本。
三、单体优先（Monolith First）：Martin Fowler 发现几乎所有成功的微服务故事，都是从一个变得太大而被分解的单体开始的；而几乎所有从头构建为微服务系统的系统都以严重的麻烦告终。微服务会产生显著的“微服务附加费”——管理一套服务的成本会拖慢团队速度。因此他主张：单体允许你探索系统的复杂性和组件边界，当复杂性增加时再裂变出微服务。四种单体优先策略：①模块化单体——仔细设计单体、注意内部模块化（含 API 边界和数据存储方式）；②边缘剥离——从单体开始逐渐剥离边缘的微服务；③整体替换——不害怕建造一个会丢弃的单体，尤其当它能让你快速进入市场；④粗粒度服务——从几个比你最终微服务更大的粗粒度服务开始，随边界稳定再分解。对于人数不多、资金不充裕、需要快速把产品推向市场的团队，“单体优先”是一个务实的选择。

**解析**

回答要点：单体 = 简单但耦合、难扩展；微服务 = 独立部署但引入分布式复杂度。核心逻辑是“先单体、后拆分”，边界靠实践探索而非预先设计。注意补充“微服务附加费”这一概念的来历与含义。

### 79. 【面试·架构】什么是服务网格（Service Mesh）？它与 Spring Cloud 的解决思路有何不同？

**答案**

一、背景：从软件层面独力应对微服务架构问题，发展到软、硬一体合力应对架构问题的时代，即“后微服务时代”（常被冠以“云原生”之名）。Kubernetes 成为容器战争胜利者标志着后微服务时代的开端，但仅从功能上看，单纯的 Kubernetes 反而不如之前的 Spring Cloud 方案，因为有些问题处于应用系统与基础设施的边缘，完全在基础设施层面很难精细化处理；而 Spring Cloud 的解决方法比较重，学习和交付成本高，需要花大量精力关注和配置与业务无关的功能实现。
二、服务网格（Service Mesh）：为解决这类问题，虚拟化基础设施引入今天被称为“服务网格”的“边车代理模式”（Sidecar Proxy）。所谓“边车”指由系统自动在服务容器（通常是 Kubernetes 的 Pod）中注入一个通信代理服务器，以类似网络安全里中间人攻击的方式进行流量劫持，在应用毫无感知的情况下悄然接管应用所有对外通信。
三、工作方式：代理除了实现正常的服务间通信（数据平面通信），还接收来自控制器的指令（控制平面通信），根据控制平面中的配置对数据平面通信的内容进行分析处理，以实现熔断、认证、度量、监控、负载均衡等各种附加功能。这样既不需要在应用层面加入额外的处理代码，也提供了几乎不亚于程序代码的精细管理能力。它对应用是透明的，不需要改动任何软件代码就可以实现服务治理。
四、与传统 Spring Cloud 思路的不同：Spring Cloud 是把服务治理能力以 SDK/代码库的形式内置到应用中（程序员需要关注安全策略、负载均衡、流量控制、路由选择等）；服务网格则把原本程序员需要关注的安全策略、负载均衡、流量控制、路由选择等基础能力下沉到基础设施层的代理组件中，并提供了自动恢复能力，让开发人员只需关注业务本身。此外服务网格提供各类服务编排和服务调用的一整套完整解决方案，不仅针对 JAVA 语言写的服务，可以支持任何语言，业务与技术完全分离、远程与本地完全透明。
五、代表技术：Istio、Envoy、Linkerd、Consul Connect、AWS App Mesh 等；Kubernetes 结合 Istio 和 Envoy 是实现 Service Mesh 的主流方案。

**解析**

回答要点：抓住“边车代理 + 控制平面/数据平面分离 + 对应用透明”三个关键词，并对比 Spring Cloud“能力在应用内(SDK)”与 Mesh“能力在基础设施内(代理)”。可补充：Service Mesh 将会成为微服务间通信的主流模式，取代 Spring Cloud 全家桶中大部分组件的功能。

### 80. 【面试·ZooKeeper】ZooKeeper 的核心功能有哪些？简述其在 Dubbo 架构中的作用。

**答案**

ZooKeeper 是一个开源的分布式协调服务，是一个典型的分布式数据一致性解决方案。它的设计目标是将那些复杂且容易出错的分布式一致性服务封装起来，构成一个高效可靠的原语集，并以一系列简单易用的接口提供给用户使用。分布式应用程序可以基于 ZooKeeper 实现诸如数据发布/订阅、负载均衡、命名服务、分布式协调/通知、集群管理、Master 选举、分布式锁和分布式队列等功能。
其四大核心功能：
1. 命名服务：被命名的实体通常是集群中的机器、提供的服务地址或远程对象等，统称为名字（Name）。通过命名服务，客户端应用能够根据指定名字来获取资源的实体、服务地址和提供者的信息。
2. 状态同步：每个节点除存储数据内容和 node 状态信息外，还存储已注册 APP 的状态信息，当某些节点或 APP 不可用，就将当前状态同步给其他服务。
3. 配置中心：解决同一应用多份配置、多个程序相同配置的集中修改问题。ZooKeeper 采用推拉相结合方式——客户端向服务端注册自己需要关注的节点，节点数据变更时服务端发送 Watcher 事件通知，客户端收到通知后主动到服务端获取最新数据。
4. 集群管理：包括集群监控与集群控制两大块，前者侧重运行时状态收集，后者侧重对集群的操作与控制（如知道当前集群有多少机器在工作、对每台机器运行时状态收集、上下线操作）。
此外，ZooKeeper 还有两大特性：一是客户端对某数据节点注册 Watcher 监听后，该节点内容或其子节点列表发生变更时会收到变更通知；二是临时节点一旦客户端与服务器之间的会话失效，该临时节点会被自动清除。Watcher 机制是 ZooKeeper 实现分布式协调服务的重要特性。
在 Dubbo 架构中的作用：ZooKeeper 担任注册中心（提供发布订阅服务）这一角色。服务生产者将自己提供的服务注册到 ZooKeeper 中心，服务消费者进行服务调用时先到 ZooKeeper 中查找服务，获取到服务生产者的详细信息之后，再去调用服务生产者的内容与数据。

**解析**

回答要点：四大功能（命名服务/状态同步/配置中心/集群管理）+ 两大特性（Watcher 通知、临时节点随会话失效自动清除）+ Dubbo 中担任注册中心。可延伸说明 ZNode 数据模型为树状结构、类似 Linux 文件系统。

### 81. 【面试·ZooKeeper】请详细描述 ZooKeeper 集群的 Leader 选举过程，并说明选举时对比投票的规则。

**答案**

一、选举触发：当集群中的 zookeeper 节点启动后，会根据配置文件中指定的节点地址进行 leader 选择操作。节点角色状态有四种：LOOKING（寻找 Leader）、LEADING、FOLLOWING、OBSERVER。
二、选举 ID：
1. ZXID（zookeeper transaction id）：每个改变 Zookeeper 状态的操作都会自动生成一个对应的 zxid，ZXID 最大的节点优先选为 Leader；
2. myid：服务器的唯一标识（SID），通过配置 myid 文件指定，集群中唯一，当 ZXID 一样时，myid 大的节点优先选为 Leader。
三、选举过程：
1. 每个 zookeeper 都会发出投票。由于是第一次选举 leader，每个节点都会把自己当做 leader 角色进行选举，投票中包含自己的 myid 和 zxid（例如 zookeeper 1 的投票为 myid 1、初始 zxid 为 0x0；zookeeper 2 的投票为 myid 2、zxid 为初始生成的值）；
2. 每个节点接受并检查对方的投票信息，比如投票时间、是否状态为 LOOKING 状态的投票；
3. 对比投票，优先检查 zxid：如果 zxid 不一样则 zxid 大的为 leader；如果 zxid 相同则继续对比 myid，myid 大的一方为 leader。
四、成为 Leader 的必要条件：Leader 要具有最高的 zxid；当集群规模是 n 时，集群中大多数的机器（至少 n/2+1）得到响应并从 follower 中选出 Leader。
五、心跳与重选：Leader 与 Follower 利用 PING 来感知对方是否存活，当 Leader 无法响应 PING 时，将重新发起 Leader 选举。当 Leader 服务器出现网络中断、崩溃退出与重启等异常情况时，ZAB 协议就会进入恢复模式并选举产生新的 Leader 服务器，过程大致为：Leader Election（选举阶段，只要有一个节点得到超半数节点的票数即可当选准 leader）→ Discovery（发现阶段，followers 跟准 leader 通信，同步最近接收的事务提议）→ Synchronization（同步阶段，利用 leader 在前一阶段获得的最新提议历史同步集群中所有副本，同步完成后准 leader 才成为真正的 leader）→ Broadcast（广播阶段，集群正式对外提供事务服务，leader 可以进行消息广播）。

**解析**

回答要点：先说触发条件与角色状态，再讲 ZXID 与 myid 两个选举 ID，然后分步描述选举过程（自荐→校验→对比 zxid→对比 myid），补充 n/2+1 的过半条件与 PING 心跳重选，最后可补 ZAB 恢复模式的四阶段。

### 82. 【面试·ZooKeeper】ZooKeeper 集群为什么通常由奇数台节点组成？请以 3 台和 4 台为例说明容错能力。

**答案**

一、可用性判定规则：整个集群中只要有超过集群数量一半的 zookeeper 正常工作，那么整个集群对外就是可用的。也就是说对于 n 台 Server，只要有 >n/2 台节点可用，整个 ZooKeeper 系统就保持可用。
二、举例说明：
1. 2 台服务器组成集群：只要有任意一台故障或宕机，剩下 1 台没有超过集群一半（1 不大于 1），该 ZooKeeper 集群就不可用了；
2. 3 台组成集群：损坏一台还剩两台，2 > 3/2（即 1.5），所以集群仍可正常运行；再损坏一台只剩 1 台，集群不可用。因此 3 台集群最多容忍 1 台故障；
3. 4 台组成集群：损坏一台还剩 3 台仍正常；损坏两台还剩 2 台，2 不大于集群数量的一半（2 不 > 2），所以集群不可用。因此 4 台集群同样最多容忍 1 台故障。
三、结论：3 台与 4 台的容错能力完全相同（都只能容忍 1 台故障），但 4 台比 3 台多消耗一台服务器资源，因此 ZooKeeper 集群通常由奇数台 Server 节点组成（3、5、7 台），以在保证容错能力的同时不浪费硬件资源。
四、相关特性：随着集群中节点数越多，写性能越差、读性能越好（读的比例越高，整体性能越好）；ZooKeeper 集群基于 Master/Slave 模型，写操作由 Leader 处理并同步给 Follower，一旦总数过半的节点成功应用了这个写操作，Leader 就认为写操作成功。

**解析**

回答要点：核心是“可用节点数必须 > n/2”。分别计算 2/3/4 台的容错能力，指出 3 台与 4 台容错相同（均容忍 1 台），故取奇数台避免浪费。可补充“节点越多写性能越差、读性能越好”。

### 83. 【面试·Kafka】Kafka 的核心概念有哪些（Producer/Consumer/Broker/Controller/Topic/Partition/Consumer Group/Replication）？请逐一说。

**答案**

1. Producer（生产者）：消息的产生者，是消息的入口，负责发布消息到 Kafka broker。
2. Consumer（消费者）：用于消费消息，即处理消息。
3. Broker：Kafka 实例，每个服务器上可以有一个或多个 Kafka 实例，假设每个 broker 对应一台服务器；每个 Kafka 集群内的 broker 都有一个不重复的编号（如 broker-0、broker-1）。
4. Controller：整个 Kafka 集群的管理者角色，任何集群范围内的状态变更都需要通过 Controller 进行。它在整个集群中是个单点服务，可以通过选举协议进行故障转移，负责主题的新建和删除、主题分区的新建与重新分配、Broker 的加入退出、触发分区 Leader 选举等。每个 Broker 里都有一个 Controller 实例，多个 Broker 的集群同时最多只有一个 Controller 对外提供集群管理服务。Controller 通过监听 Zookeeper 节点的变动来监听集群变化事件，其保存集群元数据、监听集群状态变化主要利用 Zookeeper 实现。
5. Topic：消息的主题，可以理解为消息的分类。一个 Topic 相当于数据库中的一张表，一条消息相当于关系数据库的一条记录；每个 broker 上都可以创建多个 topic。物理上不同 topic 的消息分开存储在不同文件夹，但用户只需指定 topic 即可生产或消费数据，不必关心数据存于何处。
6. Partition（分区）：是物理上的概念，每个 topic 分割为一个或多个 partition，当创建 topic 时可指定 partition 数量。partition 的表现形式就是一个个文件夹，文件夹下存储该 partition 的数据和索引文件。分区可以实现负载均衡、提高吞吐量。同一个 topic 在不同分区的数据是不重复的，一般 Partition 数不要超过节点数；同一个 partition 数据是有顺序的，但不同的 partition 则是无序的。
7. Consumer Group（消费者组）：每个 consumer 属于一个特定的 consumer group（不指定 group name 则属于默认 group）。同一 topic 的一条消息只能被同一个 consumer group 内的一个 consumer 消费，类似于一对一的单播机制；但多个 consumer group 可同时消费这一消息，类似于一对多的多播机制。默认消费组的多个消费者共享消息，从而实现负载均衡。
8. Replication（副本）：同样数据的副本，包括 leader 和 follower 的副本数，基于数据安全建议至少 2 个，是 Kafka 高可靠性的保障。副本数不能超过集群节点的数量。注意 Kafka 中的副本（leader+follower）数包括主分片数，而 Elasticsearch 中的副本数（follower）不包括主分片数。
附：AR（Assigned Replicas，所有副本统称）= ISR（In Sync Replicas，与 leader 保持同步的副本，含 leader）+ OSR（Out-of-Sync Replicas，同步滞后的 follower）。

**解析**

回答要点：按“消息入口—处理—载体—管理—分类—物理切分—消费分组—冗余保障”的顺序串讲，重点讲清 Controller 的单点与故障转移、Consumer Group 的单播/多播机制、Replication 与 AR/ISR/OSR 的关系。

### 84. 【面试·Kafka】Kafka 如何保证消息顺序性和高可用？分区与副本机制是如何工作的？

**答案**

一、顺序性保证：Kafka 保证一个 Partition 内的消息是有序的，分区间数据是无序的。因为同一 partition 的数据写入和读取都按顺序追加/顺序读取。如果对数据的顺序有要求，应在创建主题时将分区数 partitions 设置为 1（此时全局有序）。
二、高可用与副本机制：
1. 为了实现数据的高可用，Kafka 为每个分区设置副本。每个分区都有一个 broker 作为 Leader、一个或多个 broker 作为 Follower，类似于 ES 中的主分片和副本分片。副本数不能超过集群节点的数量，基于数据安全建议至少 2 个。
2. 举例：假设分区为 3（分区 0-2），副本为 3，即每个分区都有一个 leader 加两个 follower。分区 0 的 leader 为服务器 A，则服务器 B、C 为 A 的 follower；分区 1 的 leader 为服务器 B，则服务器 A、C 为 B 的 follower；分区 2 的 leader 为 C，则服务器 A、B 为 C 的 follower。这样分区即 leader 分布在不同的 kafka 服务器，并且有对应 follower 分布在和 leader 不同的服务器上。
3. 读写机制：每个 Kafka Topic 的分区都有一个 leader 和零个或多个 follower；leader 负责所有客户端请求的读写操作（Kafka 2.4 新版本后 follower 也支持读），follower 则复制 leader 的数据。
4. 领导者选举：当新的分区创建时，Kafka 选择 ISR 列表中的第一个副本作为 leader；当 leader 失败或无法与 ZooKeeper 通信时，会重新选举新的 leader，这个过程称为领导者故障转移（leader failover）。详细步骤：leader 故障后 ZooKeeper 检测到它的会话过期 → 通知所有副本进行领导者选举 → 副本们查看在 ZooKeeper 中存储的元数据并确定新 leader，规则是选取副本集合（ISR）中最新的副本 → 新 leader 选出后 ZooKeeper 通知所有副本更新元数据。
三、分区与副本的优势：实现存储空间的横向扩容（将多个 kafka 服务器的空间组合利用）；提升性能，多服务器并行读写；实现分区 leader 分布在不同 kafka 服务器，并有对应 follower 分布在和 leader 不同的服务器上，从而具备容错能力。
四、演进：Kafka 2.8.0 版本开始增加 KRaft 模式，不再需要 ZooKeeper，而是使用内置的 Raft 协议来进行元数据管理和领导者选举；Kafka 4.0.0 版本起不再支持 ZooKeeper。

**解析**

回答要点：顺序性 = Partition 内有序（分区数设为 1 可全局有序）；高可用 = 副本机制（leader/follower）+ ISR + leader 故障转移。注意说明 Kafka 2.4 后 follower 也支持读、2.8 起引入 KRaft。

### 85. 【面试·Kafka】Kafka 如何配置实现“强一致性”？acks 的三个取值分别代表什么语义？

**答案**

一、为什么需要配置：Kafka 可以配置为提供强一致性的语义，但这是以牺牲一定的性能为代价的。Kafka 中数据分布在各个分区上，每个分区都有一个 leader 和若干 follower，leader 负责处理所有读写请求，follower 复制 leader 的数据，这种设计确保了数据的高可用性和容错性。
然而，为了保证高性能和低延迟，Kafka 允许 leader 在数据还未被所有的 follower 复制之前就将写操作确认为成功。这就带来一种可能：在 leader 确认写操作成功后、新数据还未被所有 follower 复制完成之前，leader 发生故障，此时新数据可能会丢失，从而造成一致性问题。
二、强一致性的配置方式：要实现强一致性，需要：
1. 将 min.insync.replicas 参数设置为大于 1，这样可以确保至少有 N 个副本确认数据写入才认为写操作成功；
2. 设置 acks 为 all 或者 -1，表示 leader 需要等待所有的 ISR（In-Sync Replicas）确认接收到消息后，才向生产者返回 ack。
这样即使 leader 发生故障，由于至少有一个 follower 已经复制了数据，新的 leader 仍然可以提供所有的数据，从而保证强一致性。
三、acks 三个取值：
1. acks=0：生产者发送消息后不等确认即认为成功。这种方式相当于没有复制，只有单个副本存储在 Leader 上；
2. acks=1：消息发送到 Leader 即认为成功，相当于异步复制。生产者只需要等待 Leader 的确认，而不需要等待 ISR 中其他副本的确认；
3. acks=all：需要等待 ISR 列表中所有同步的 Slave 都确认才认为成功，相当于同步复制。生产者需要等待 ISR 中所有副本都写入成功后才认为消息发送成功。
四、结论：Kafka 可以配置为提供强一致性，但这可能会影响其性能和吞吐量，实际使用中需要根据自己的业务需求在一致性和性能之间进行权衡。

**解析**

回答要点：强一致 = min.insync.replicas>1 + acks=all/-1；acks 三档分别对应“不确认/仅 Leader 确认/等所有 ISR 确认”，对应“无复制/异步复制/同步复制”。最后一定要点出“一致性与性能的权衡”。

### 86. 【面试·Kafka】Kafka 消息积压的常见原因有哪些？排查手段与解决方案分别是什么？

**答案**

一、消息积压定义：消息积压是指在消息传递系统中，积累了大量未被处理或未被消费的消息。
二、常见原因：
1. 消费者处理速度慢：消费者处理速度不足以跟上生产者速度，可能因消费者逻辑复杂、消费者数量不足、消费者宕机或网络延迟等引起；
2. 消费者宕机：某个消费者宕机，其负责处理的分区将没有消费者消费消息，导致消息在该分区上积压；
3. 网络问题：网络故障导致生产者与消费者之间的通信延迟或中断；
4. 硬件资源不足：Kafka 集群所在机器（生产者、消费者、Broker）CPU、内存或磁盘等资源不足；
5. 分区不均匀：某些分区负载比其他分区更高，可能因分区数量设置不合理、数据分布不均匀引起；
6. 生产者速度过快：生产者生产速度过快而消费者无法及时处理；
7. 配置不当：副本数、分区数、消费者数量等参数配置不合理；
8. 异常情况：突发性硬件故障、网络故障、软件 bug 等。
三、发现积压的手段：
1. 监控工具：Kafka Manager、Burrow、Kafka Offset Monitor 等，监控每个分区的偏移量和消费者组状态，通过检查偏移量的增长速度判断是否有积压；
2. Consumer Lag：消费者组相对于生产者的消息偏移量的差异，Lag 增长较快可能表示积压；
3. Kafka Logs 目录：检查每个分区的日志目录，查看是否有大量未消费消息；
4. Kafka Broker Metrics：如消息入队速率、出队速率等；
5. 操作系统资源：监控 CPU、内存、磁盘等；
6. 警报系统：指标达到阈值时触发警报。
命令行方式：kafka-consumer-groups.sh --bootstrap-server {kafka连接地址} --describe --group {消费组} | --all-groups，其中 LAG 表示每个 Topic 的总堆积数；当前消费的 offset 和最后一条 offset 差距很大，说明有大量数据积压。
四、解决方案：
1. 增加消费者数量：提高处理速度；
2. 扩展 Kafka 集群：消息积压由于吞吐量达到极限时，扩大集群规模增加处理能力；
3. 数据分区：合理划分数据分区提高并行处理能力；
4. 数据清理：定期清理过期数据和日志文件，释放磁盘空间并提高性能；
5. 优化消费者代码：检查性能瓶颈或不必要的延迟；
6. 调整 Kafka 配置：增加分区数量、调整副本数量、调整日志清理策略等；
7. 监控和警报：设置监控系统及时发现并发送警报；
8. 故障排除：检查系统日志查找问题源并采取措施。

**解析**

回答要点：原因分“消费端慢/宕机、生产者过快、网络与硬件、分区与配置、异常”；排查核心指标是 Consumer Lag（CURRENT-OFFSET 与 LOG-END-OFFSET 的差距）；解决思路是“扩消费者 / 扩集群 / 调分区 / 清数据 / 优代码 / 改配置 / 加监控”。

### 87. 【面试·Kafka】请对比 ZooKeeper 模式与 KRaft 模式，说明 Kafka 为什么逐步弃用 ZooKeeper。

**答案**

一、ZooKeeper 模式：4.0 以前版本 Kafka 依赖 Zookeeper 服务（Kafka 4.0.0 版本不再支持 Zookeeper）。ZooKeeper 承担了多项职责：
1. Broker 依赖于 Zookeeper，每个 Broker 的 id 和 Topic、Partition 这些元数据信息都会写入 Zookeeper 的 ZNode 节点中；
2. Consumer 依赖于 Zookeeper，每消费完一条消息会将产生的 offset 保存到 Zookeeper 中（kafka 0.9 之前 Consumer 的 offset 存储在 Zookeeper 中，kafka 0.9 以后 offset 存储在本地）；
3. Partition 依赖于 Zookeeper，Partition 完成 Replication 备份后选举出一个 Leader，依托于 Zookeeper 的选举机制实现。
对应存储结构：/brokers/topics/[topic]、/brokers/topics/[topic]/partitions/[partitionId]/state、/brokers/ids/[0...N]、/controller（存储中央控制器所在 kafka broker 的信息）、/consumers/[groupId]/ids/[consumerIdstring]、/consumers/[groupId]/owners/[topic]/[partitionid]。
二、KRaft 模式：Kafka 2.8.0 版本开始增加 KRaft（KRaft 是 Kafka Raft 协议模式的简称）模式，这个模式下 Kafka 不再需要 ZooKeeper，而是使用内置的 Raft 协议来进行元数据的管理和领导者选举。Raft 协议是一种为分布式系统提供一致性的算法，它更易于理解和实施，同时也保证了系统的可用性和数据的一致性。部署要点：每个节点同时作为 Broker 和 Controller 运行（process.roles=broker,controller），需配置 node.id 与 controller.quorum.voters（格式 node.id@host:port），所有节点使用同一集群 ID（kafka-storage.sh random-uuid 生成），并用 kafka-storage.sh format 初始化元数据存储后再启动。
三、弃用 ZooKeeper 的原因：
1. 架构简化：不再需要额外部署和维护一套独立的 ZooKeeper 集群，降低了运维复杂度与组件间依赖；
2. 元数据管理更内聚：元数据由 Kafka 自身基于 Raft 管理，避免元数据跨系统存储带来的同步与一致性问题；
3. 一致性与可用性：Raft 通过选举算法确保领导者唯一性，所有写操作都通过领导者完成，可确保所有复制节点数据一致；
4. 演进节奏：2021 年 4 月 19 日 Kafka 2.8.0 正式发布，通过自我管理的仲裁替代 ZooKeeper；到 Kafka 4.0.0 版本则不再支持 ZooKeeper，强制使用 KRaft。

**解析**

回答要点：先讲 ZooKeeper 在旧版中承担的 3 类元数据职责（Broker 元数据/offset/分区 Leader 选举），再讲 KRaft 基于 Raft 自管理元数据，最后归纳“简化架构、内聚元数据、一致性更强、官方演进路线”四点原因。

### 88. 【面试·Nacos】Nacos 与 Eureka 的区别是什么？为什么 Nacos 在国内更受欢迎？

**答案**

一、定位区别：Nacos 是一个更全面的服务管理平台，不仅提供服务注册与发现功能，还集成了配置管理、动态配置推送、服务元数据管理等特性，这意味着使用 Nacos 可以同时解决服务发现和服务配置管理的问题；此项目由阿里巴巴负责持续迭代更新。Eureka 主要聚焦于服务注册与发现，虽然也具备一定的配置管理能力，但相较于 Nacos 其功能较为单一，主要被设计为高度可用的服务发现服务器，而且其自身也需要做为微服务由程序员自行开发编码和部署，更重要的是此项目当前已不再更新（2023-06-22 已停更）。
二、一致性模型区别：Nacos 默认使用 AP（Availability 和 Partition tolerance）模式，存在非临时实例时会采用 CP（Consistency 和 Partition tolerance）模式；Eureka 采用 AP 模式。也就是说 Nacos 可根据场景在 AP/CP 之间切换，而 Eureka 只支持 AP。
三、服务变更通知区别：Nacos 中消费者定时向注册中心 PULL 拉取提供者信息并加以缓存，如果提供者有变化，nacos 会主动向消费者 PUSH 推送消息通知；而 Eureka 不支持主动 PUSH，只能由客户端定时拉取，因此存在服务感知延迟。
四、实例类型区别：Nacos 支持临时实例（服务提供者定期主动发送心跳，一段时间收不到心跳则删除此实例）和非临时/永久实例（Nacos 主动定时监测，实例异常不删除只标记异常并等待恢复）；Eureka 主要基于客户端心跳续约。
五、为什么国内更受欢迎：①Spring Cloud Alibaba 的组件在国内用户中的受欢迎程度已超过 Spring Cloud 官方默认提供的一些组件，Nacos 和 RocketMQ 已逐渐成为国内分布式注册配置中心和分布式消息的事实标准，广泛应用于大量中小企业的生产环境；②Nacos 是“注册中心 + 配置中心”二合一，减少了一套组件（可替代 Eureka + Spring Cloud Config / Apollo 的部分职能）；③有阿里巴巴持续投入与活跃的中文社区、文档与生态（与 Dubbo、Spring Cloud Alibaba、APISIX 等无缝配合）；④支持 AP/CP 切换、支持主动推送、支持命名空间/分组多环境隔离，功能更贴合国内企业的落地需求。

**解析**

回答要点：从“功能范围（发现+配置）/ 一致性模型（AP 可切 CP vs 纯 AP）/ 变更通知（支持 Push vs 仅 Pull）/ 实例类型 / 项目活跃度（Eureka 已停更）”五个维度对比，再说明国内流行的生态因素。

### 89. 【面试·Nacos】Nacos 注册中心的工作机制是怎样的？临时实例与非临时实例有何区别？

**答案**

一、为什么需要注册中心：随着应用架构向微服务架构迁移，服务数量的增加和动态部署、动态扩展的特性，使得服务地址和端口在运行时随时可变。因此需要一个组件管理当前注册到服务注册与发现中心的微服务实例元数据信息，包括服务实例的服务名、IP 地址、端口号、服务描述和服务状态等；与注册到中心的微服务实例维持心跳、定期检查注册表中的服务实例是否在线，并剔除无效服务实例信息；并提供服务发现能力，为服务调用方提供服务提供方的服务实例元数据。
二、服务提供者分类：
1. 临时实例：服务提供者定期周期主动向 nacos 发送心跳监测报告，如果一段时间后 nacos 无法收到心跳，则删除此实例；
2. 非临时实例（永久实例）：nacos 主动定时监测此类实例，如果提供者实例异常，则并不会删除，只是标记此实例异常，等待此实例恢复。
三、服务消费者：消费者定时向 nacos 注册中心 PULL 拉取提供者信息，并加以缓存；如果提供者有变化，nacos 会主动向消费者 PUSH 推送消息通知（Eureka 不支持主动 PUSH）。
四、集群模式与一致性：Nacos 默认使用 AP（Availability 和 Partition tolerance）模式，存在非临时实例时，会采用 CP（Consistency 和 Partition tolerance）模式；Eureka 采用 AP 模式。集群数据一致性实现：CP 模式基于强一致性协议 Raft，AP 模式基于阿里的 Distro（基于 Gossip 和 Eureka 协议优化而来）最终一致性的 AP 分布式协议。
五、健康检查能力：Nacos 提供对服务的实时健康检查，阻止向不健康的主机或服务实例发送请求。它支持传输层（PING 或 TCP）和应用层（如 HTTP、MySQL、用户自定义）的健康检查；对于复杂的云环境和网络拓扑环境（如 VPC、边缘网络），Nacos 提供 agent 上报模式和服务端主动检测 2 种健康检查模式，并提供了统一的健康检查仪表盘。

**解析**

回答要点：核心是“临时实例=客户端主动心跳、丢失即删除；非临时实例=服务端主动探测、异常只标记不删除”。务必补充默认 AP、存在非临时实例转 CP、CP 用 Raft / AP 用 Distro，以及支持 Push 通知这一点。

### 90. 【面试·Nacos】Nacos 支持动态配置管理，配置变更后客户端如何感知？请说明命名空间、分组、DataId 的作用与关系。

**答案**

一、配置模型三要素：
1. 命名空间（Namespace）：用于隔离不同环境或不同租户的配置，例如创建名为 dev 的名称空间用于开发环境；在 Spring Boot 中通过 spring.cloud.nacos.config.namespace=dev 指定；
2. 分组（Group）：对配置进一步分类，默认值为 DEFAULT_GROUP，通过 spring.cloud.nacos.config.group 指定；
3. DataId：配置文件的名称（配置项标识），通过 spring.cloud.nacos.config.prefix 与 file-extension 组合而成，例如 prefix=api-service + file-extension=yml 即对应配置文件 api-service.yml。
Namespace + Group + DataId 三者共同唯一确定一个配置项。在 Nacos 控制台配置时需同时选择这三级。
二、配置变更感知与自动刷新：Spring Boot 应用在 bootstrap.properties 中配置：
spring.application.name=cloud-api
spring.cloud.nacos.server-addr=nacos.wang.org:8848
spring.cloud.nacos.config.namespace=dev
spring.cloud.nacos.config.group=DEFAULT_GROUP
spring.cloud.nacos.config.prefix=api-service
spring.profiles.active=dev
spring.cloud.nacos.config.auto-refreshed=true
spring.cloud.nacos.config.file-extension=yml
spring.cloud.nacos.discovery.server-addr=nacos.wang.org:8848
spring.cloud.nacos.discovery.namespace=dev
其中 key 的两个要点是 auto-refreshed=true 开启配置自动刷新，以及 file-extension 与实际配置格式一致。应用启动时从 Nacos 拉取配置并监听变更，配置中心在配置发生变化时会推送通知，客户端刷新本地配置，因此无需重新部署应用。
三、动态配置服务的价值：动态配置服务可以让您以中心化、外部化和动态化的方式管理所有环境的应用配置和服务配置；动态配置消除了配置变更时重新部署应用和服务的需要，让配置管理变得更加高效和敏捷；配置中心化管理让实现无状态服务变得更简单，让服务按需弹性扩展变得更容易。Nacos 还提供配置版本跟踪、金丝雀发布、一键回滚配置以及客户端配置更新状态跟踪等一系列开箱即用的配置管理特性。
四、实操提示：课件案例中把 JAVA 应用连接 Redis 的配置（host、port、password、database）写入 Nacos 的 dev 名称空间、DataID 为 api-service 的配置中；修改配置有两种方式——方法 1 修改配置后重新编译，方法 2 无需重新编译，直接把 jar 改后缀为 zip 解压，修改 BOOT-INF/classes/bootstrap.properties 后再改回 jar。

**解析**

回答要点：讲清 Namespace/Group/DataId 三级定位，重点说明 Spring Boot 通过 bootstrap.properties 中的 namespace/group/prefix/file-extension + auto-refreshed=true 接入，配置变更由配置中心推送、客户端刷新，无需重启或重新部署。

### 91. 【面试·Nacos】Nacos 集群部署有哪些注意事项？请说明集群端口规划与 SLB/域名接入的推荐做法。

**答案**

一、集群基本要求：
1. 3 个或 3 个以上 Nacos 节点才能构成集群；
2. 环境要求 64 bit OS（推荐 Linux）、64 bit JDK 1.8+，建议 2 核 CPU / 4G 内存及其以上，生产环境 3 个节点及其以上；
3. 部署模式有三种：单机模式（用于测试和单机试用）、集群模式（用于生产环境，确保高可用）、多集群模式（用于多数据中心场景）；当前推荐的稳定版本为 2.X。
二、数据源：如果使用内置数据源无需任何配置；使用外置数据源时，生产使用建议至少主备模式，或者采用高可用数据库。使用 MySQL 需初始化数据库（执行 conf/mysql-schema.sql），并在所有集群节点修改 application.properties 配置数据源（spring.sql.init.platform=mysql、db.num、db.url.0、db.user.0、db.password.0）。
三、集群配置：在 nacos 解压目录 conf 下的 cluster.conf 中，每行配置一个 ip:port，所有集群节点都要修改。
四、端口规划（端口 = 主端口 + 偏移量）：8848（偏移 0，主端口，客户端、控制台及 OpenAPI 所使用的 HTTP 端口）、9848（偏移 1000，客户端 gRPC 请求服务端端口）、9849（偏移 1001，服务端 gRPC 请求服务端端口，用于服务间同步）、7848（偏移 -1000，raft 请求服务端端口）。注意：9849 和 7848 端口为服务端之间的通信端口，请勿暴露到外部网络环境和客户端侧。
五、接入方式（三种）：
1. http://ip1:port/openAPI —— 直连 ip 模式，机器挂则需要修改 ip 才可以使用；
2. http://SLB:port/openAPI —— 挂载 SLB 模式（内网 SLB，不可暴露到公网，以免带来安全风险），直连 SLB 即可，下面挂 server 真实 ip，可读性不好；
3. http://nacos.com:port/openAPI —— 域名 + SLB 模式（内网 SLB，不可暴露到公网），可读性好，而且换 ip 方便，推荐模式。
即把所有服务列表放到一个 VIP 下面（内网 VIP/SLB），然后挂到一个域名下面，域名指向 VIP/SLB。注意：使用 VIP/nginx 请求时，需要配置成 TCP 转发，不能配置 http2 转发，否则连接会被 nginx 断开。
六、高可用补充：课件案例用 haproxy + keepalived 实现负载均衡和高可用（VIP 10.0.0.100，haproxy1+keepalived 10.0.0.101、haproxy2+keepalived 10.0.0.102，nacos1/2/3 为 10.0.0.201~203，MySQL 10.0.0.200）。
七、安全提示：Nacos 是内部微服务组件，需要在可信的内部网络中运行，不可暴露在公网环境；生产环境应开启鉴权（2.X 默认不开启、3.X 默认开启）。

**解析**

回答要点：必答“3 节点起、推荐外置高可用 MySQL、cluster.conf 配 ip:port”；端口记“8848/9848/9849/7848”四个并强调 9849/7848 不可外露；接入推荐“内网 VIP + SLB + 域名”第三种模式且必须 TCP 转发。

### 92. 【面试·Sentinel】什么是微服务雪崩？解决雪崩问题的常见方式有哪些？

**答案**

一、雪崩的定义：随着微服务的流行，服务和服务之间的调用导致服务的稳定性问题变得越来越重要。雪崩问题即微服务调用链路中的某个服务故障，引起整个链路中的所有微服务都不可用。
二、解决雪崩问题的常见方式有四种：
1. 超时处理：设定超时时间，请求超过一定时间没有响应就返回错误信息，不会无休止等待；
2. 流量控制：限制业务访问的 QPS，避免服务因流量的突增而故障；
3. 熔断降级：由断路器统计业务执行的异常比例，如果超出阈值则会熔断该业务，拦截访问该业务的一切请求。当系统资源（如 CPU、内存、线程池）紧张或某服务负载过高时，主动暂时舍弃部分非核心功能或降低服务质量，以保证核心功能的可用性，通过牺牲部分功能来维持系统整体的可用性，避免因局部问题导致全局崩溃；
4. 舱壁模式：限定每个业务能使用的线程数，避免耗尽整个 tomcat 的资源，因此也叫线程隔离。
三、Sentinel 对应的能力：Sentinel 主要以流量为切入点，从流量路由、流量控制、流量整形、熔断降级、系统自适应过载保护、热点流量防护等多个维度帮助开发者保障微服务的稳定性：
· 流量控制——根据系统处理能力对流量进行控制，控制角度包括资源的调用关系、运行指标（QPS、线程池、系统负载等）、控制的效果（直接限流、冷启动、排队等）；
· 熔断降级——当调用链路中某个资源出现不稳定（timeout、异常比例升高）时，对该资源的调用进行限制并让请求快速失败，避免影响其它资源导致雪崩；资源被降级后在降级时间窗口内对该资源的调用都自动熔断（默认抛出 DegradeException）；
· 系统负载保护——让系统入口流量和系统负载达到一个平衡，保证系统在能力范围之内处理最多的请求，防止集群环境下因单机流量被转发而引发连锁崩溃。

**解析**

回答要点：先定义雪崩（链路中一个服务故障导致整条链路不可用），再列出四种应对方式（超时处理/流量控制/熔断降级/舱壁模式），最后说明 Sentinel 的流量控制、熔断降级、系统自适应保护三项能力如何对应。

### 93. 【面试·Sentinel】Sentinel 与 Hystrix 在隔离策略和熔断降级上的区别是什么？Sentinel 的 Slot Chain 包含哪些 slot？

**答案**

一、隔离策略的区别：
· Hystrix 通过线程池的方式对依赖（即资源）进行隔离，好处是资源和资源之间做到最彻底的隔离，缺点是除了增加线程切换的成本，还需要预先给各个资源做线程池大小的分配；
· Sentinel 通过限制资源并发线程的数量来减少不稳定资源对其它资源的影响，没有线程切换的损耗，也不需要预先分配线程池大小；当某个资源出现不稳定（如响应时间变长）时，会造成线程数逐步堆积，堆积到一定数量后对该资源的新请求就被拒绝，堆积的线程完成任务后才开始继续接收请求。
二、熔断降级手段的区别：
· Hystrix 的熔断降级策略基于异常比例（最后更新 2018-11-17）；
· Sentinel 的熔断降级策略支持慢调用比例、异常比例、异常数；此外 Sentinel 还可以通过响应时间对资源进行降级——当依赖资源响应时间过长后，所有对该资源的访问都会被直接拒绝，直到过了指定的时间窗口之后才重新恢复。
三、功能对比要点（课件表格）：Sentinel 在动态规则配置（支持近十种动态数据源）、集群流控、流量整形（支持预热模式与匀速排队）、系统自适应保护、热点识别/防护、多语言支持（Java/Go/C++）、Service Mesh 支持（Envoy/Istio）、开箱即用控制台等方面均强于 Hystrix；Hystrix 与 resilience4j 均不支持集群流控、系统自适应保护与热点防护。实时统计实现上：Sentinel 用滑动窗口 LeapArray，Hystrix 用基于 RxJava 的滑动窗口，resilience4j 用 Ring Bit Buffer。
四、Slot Chain 包含的 slot 及其职责：
1. NodeSelectorSlot——负责收集资源的路径，并将这些资源的调用路径以树状结构存储起来，用于根据调用路径来限流降级；
2. ClusterBuilderSlot——用于存储资源的统计信息以及调用者信息（如该资源的 RT、QPS、thread count 等），作为多维度限流、降级的依据；
3. StatisticSlot——用于记录、统计不同维度的 runtime 指标监控信息，底层采用高性能滑动窗口数据结构 LeapArray 统计实时秒级指标；
4. FlowSlot——用于根据预设的限流规则以及前面 slot 统计的状态来进行流量控制；
5. AuthoritySlot——根据配置的黑白名单和调用来源信息做黑白名单控制；
6. DegradeSlot——通过统计信息以及预设规则来做熔断降级；
7. SystemSlot——通过系统的状态（如 load1 等）来控制总的入口流量。
Sentinel 将 ProcessorSlot 作为 SPI 接口进行扩展（1.7.2 版本以前 SlotChainBuilder 作为 SPI），因此可以自行加入自定义 slot 并编排 slot 间顺序。

**解析**

回答要点：隔离策略对比是“Hystrix 线程池隔离 vs Sentinel 并发线程数限制”；熔断策略对比是“Hystrix 仅异常比例 vs Sentinel 慢调用比例/异常比例/异常数 + 响应时间降级”；Slot Chain 按顺序记忆 NodeSelectorSlot → ClusterBuilderSlot → StatisticSlot → FlowSlot → AuthoritySlot → DegradeSlot → SystemSlot。

### 94. 【面试·Seata】什么是分布式事务？Seata 的三个核心角色 TC/TM/RM 分别承担什么职责？

**答案**

一、分布式事务的定义与由来：在传统单体应用中，业务由 3 个模块组成、使用单个本地数据源，本地事务即可保证数据一致性。但在微服务架构中，这 3 个模块被设计为 3 个不同数据源之上的 3 个服务（模式：每个服务的数据库），每个服务中的数据一致性由本地事务保证，但整个业务逻辑范围的数据一致性就成了问题。典型场景：微服务下单业务，下单时调用订单服务创建订单并写入数据库，然后订单服务调用账户服务和库存服务，账户服务负责扣减用户余额、库存服务负责扣减商品库存，若其中一步失败则整体数据不一致。
定义：一个分布式事务是一个全局事务，它是由一批分支事务组成的，而通常分支事务就是本地事务。
二、Seata 简介：Seata（Simple Extensible Autonomous Transaction Architecture，简单可扩展自主交易架构）是一款开源的分布式事务解决方案，致力于在微服务架构下提供高性能和简单易用的分布式事务服务。2019 年 1 月正式对外开源，2023 年 10 月 29 日捐赠给 Apache 基金会并通过投票，加入 Apache 孵化器项目。
三、三个核心角色：
1. TC（Transaction Coordinator 事务协调器）：维护所有全局和分支事务的状态，驱动全局提交或回滚，由 Seata Server 实现（Server 端为单独服务端部署）；
2. TM（Transaction Manager 事务管理器）：定义一个全局事务的范围，开始全局事务、提交或回滚全局事务，由应用实现；
3. RM（Resource Manager 资源管理器）：管理分支事务处理的资源，与 TC 通信以注册分支事务并报告分支事务的状态，并驱动分支事务提交或回滚，由应用实现。
四、典型生命周期：
1. TM 请求 TC 开始新的全局事务，TC 生成代表全局事务的 XID；
2. XID 通过微服务的调用链传播；
3. RM 将本地事务作为 XID 对应的全局事务的分支注册到 TC；
4. TM 请求 TC 提交或回滚 XID 对应的全局事务；
5. TC 驱动 XID 对应的全局事务下的所有分支事务完成分支提交或回滚。
五、工作模型：一个分布式的全局事务整体是“两阶段提交”的模型，全局事务由若干分支事务组成，每个分支事务都需具备一阶段 prepare 行为、二阶段 commit 或 rollback 行为。在两阶段提交协议中，资源管理器 RM 需提供“准备”、“提交”和“回滚”3 个操作；事务管理器 TM 分 2 阶段协调所有资源管理器：第一阶段询问所有 RM “准备”是否成功，若全部成功则第二阶段执行所有资源的“提交”操作，否则执行所有资源的“回滚”操作，保证所有资源的最终状态一致（要么全部提交要么全部回滚）。

**解析**

回答要点：先用下单扣余额扣库存的例子说明分布式事务问题，再给出“全局事务 = 一批分支事务”的定义；三角色按“TC 由 Seata Server 实现、TM/RM 由应用实现”区分，最后补 XID 传播与两阶段提交模型。

### 95. 【面试·Seata】请对比 Seata 的 AT、XA、TCC、SAGA 四种事务模式（一致性、隔离性、代码侵入、性能、适用场景）。

**答案**

Seata 为用户提供了 AT、TCC、SAGA 和 XA 四种事务模式，打造一站式的分布式解决方案。对比维度如下：
一、一致性：XA 为强一致；AT 为弱一致（最终一致，AP 模式工作，存在数据不一致的中间状态）；TCC 为弱一致；SAGA 为最终一致。
二、隔离性：XA 完全隔离；AT 基于全局锁隔离；TCC 基于资源预留隔离；SAGA 无隔离（不保证隔离性，没有锁，会有脏写）。
三、代码侵入性：XA 无侵入；AT 无侵入；TCC 有侵入，要编写 Try/Confirm/Cancel 三个接口；SAGA 要编写状态机和补偿业务。
四、性能：XA 差（prepare 后分支事务进入阻塞阶段，收到 commit 或 rollback 前必须阻塞等待，事务资源长时间得不到释放、锁定周期长且应用层无法干预）；AT 好；TCC 非常好（一阶段完成直接提交事务、无需生成快照、无需全局锁）；SAGA 非常好（一阶段提交本地事务、无锁、事件驱动架构参与者可异步执行、高吞吐），但取决于第三方服务。
五、适用场景：XA 适用于对一致性、隔离性有高要求的业务（如金融行业并发量不大但数据很重要的场景），以及想迁移到 Seata 平台基于 XA 协议的老应用、AT 模式未适配的数据库应用；AT 适用于基于关系型数据库的大多数分布式事务场景（高并发互联网应用，允许数据出现短时不一致，可通过对账程序或补录保证最终一致性），是 Seata 的默认模式、应用最多；TCC 适用于对性能要求较高的事务（核心系统等对性能有很高要求的场景），不依赖底层数据库事务、可跨数据库跨应用资源管理，但实现复杂、需考虑 Confirm 和 Cancel 的失败情况并做好幂等处理；SAGA 适用于业务流程长、业务流程多的场景，以及参与者包含其它公司或遗留系统服务、无法提供 TCC 模式要求的三个接口的场景（例如调用支付宝支付接口→出库失败→调用支付宝退款接口）。
六、原理补充：
· XA —— 基于数据库的 XA 协议实现 2PC，XA 规范由 X/Open 组织定义，Seata 支持 MySQL、Oracle、PostgreSQL 和 MariaDB；XM 模式使用上与 AT 唯一区别是数据源代理用 DataSourceProxyXA 替代 DataSourceProxy；
· AT —— 阿里 SEATA 独有模式，通过生成反向 SQL 实现数据回滚，需在数据库额外附加 UNDO_LOG 表记录数据快照，支持 MySQL、Oracle、PostgreSQL、TiDB、MariaDB；
· TCC —— Try 负责资源检查和预留、Confirm 执行真正业务、Cancel 执行预留资源取消；
· SAGA —— 长事务解决方案，将长事务拆分成一系列短事务，一阶段直接提交本地事务、二阶段成功则什么都不做、失败则通过补偿业务回滚，理论基础是 Hector & Kenneth 于 1987 年发表的论文 Sagas。
七、XA 与 AT 的核心区别：XA 第一阶段不提交事务、锁定资源，AT 第一阶段直接提交、不锁定资源；XA 依赖数据库机制实现回滚，AT 利用数据快照实现数据回滚。

**解析**

回答要点：用“一致性/隔离性/侵入性/性能/场景”五维表格逐一对比；记忆口诀：XA 强一致但性能差、AT 默认且无侵入、TCC 性能最好但侵入大、SAGA 适合长流程。补充 XA 与 AT 的两点本质区别（是否提交事务、回滚依赖机制）。

### 96. 【面试·Gateway】为什么要使用 API 网关？API 网关的核心功能有哪些？

**答案**

一、什么是 API 网关：近几年来移动应用与企业间互联需求的兴起，从以前单一的 Web 应用扩展到多种使用场景，且每种场景对后台服务的要求都不尽相同，这不仅增加了后台服务的响应量，还增加了后台服务的复杂性。随着微服务架构概念的提出，API 网关成为了微服务架构的一个标配组件。API 网关作用就是把各个微服务对外提供的 API 汇聚起来，让外界看起来是一个统一的入口，即 API 网关就是所有微服务项目的统一入口，相当于传统的代理服务功能，还具有一些更高级的功能。
二、为什么要使用：微服务的应用可能部署在不同机房、不同地区、不同域名下，此时客户端（浏览器/手机/软件工具）想要请求对应的服务，都需要知道应用所在主机的具体 IP 或者域名 URL，当微服务实例众多时，这是非常难以记忆的，对于客户端来说也太复杂难以维护。有了网关之后，客户端相关的请求直接发送到网关，由网关根据请求标识解析判断出具体的微服务地址，再把请求转发到微服务实例，这其中的“记忆功能”就全部交由网关来操作了。
三、核心功能：
1. 路由转发——接收外界请求，通过网关的路由转发到后端的服务上，和传统的反向代理功能类似。此功能是 API 网关的最核心功能；
2. 过滤器——自行定制实现。过滤器中默认提供了多种内置功能，还支持额外的自定义功能，比较常用的有网关的容错、限流以及请求及响应的额外处理。
此外，API 网关还实现了微服务网关的额外功能，包含：负载均衡、路由转发、身份认证、权限安全、请求限流、监控/指标等功能。
四、主流解决方案：
1. Spring Cloud Netflix Zuul——基于 Spring Cloud 的 API 网关，属于 Spring Cloud Netflix 的一个组件，具有灵活、简单的特点，但基于 Servlet 实现、属于阻塞式编程实现、性能较低，其版本更新依赖于 Netflix Zuul，在早期 Spring Cloud 中使用比较多；
2. Spring Cloud Gateway——基于 Spring 生态系统构建的 API 网关，基于 Spring 5 中提供的 WebFlux 实现、响应式编程，具有更好的性能，目标是替代 Zuul；
3. APISIX——Apache 基金会下的云原生、高性能、可扩展的微服务 API 开源网关，基于 OpenResty（Nginx+Lua）和 etcd 实现，具有动态路由和热插件加载的特点。

**解析**

回答要点：先说明“微服务实例众多、地址难记忆 → 统一入口”的动机，再强调路由转发是最核心功能、过滤器负责容错与限流等横切能力，最后列出 Zuul/Gateway/APISIX 三种方案及各自特点。

### 97. 【面试·Gateway】Spring Cloud Gateway 与 Zuul、APISIX 相比有什么优势？请说明其 Route 的组成与断言、过滤器机制。

**答案**

一、与 Zuul 的对比优势：Zuul 属于 Spring Cloud Netflix 的组件，基于 Servlet 的实现，属于阻塞式编程实现，性能较低，其版本更新都依赖于 Netflix Zuul；而 Spring Cloud Gateway 基于 Spring 5 中提供的 WebFlux 实现，基于响应式编程实现，具有更好的性能，由 Spring 自己推出、完全依赖 Spring 自家产品，符合 Spring 战略意义、更新版本等都由 Spring 自己把控，是 Spring Cloud 全家桶的一部分。Gateway 作为 Spring Cloud 生态系统中的网关，目标是替代 Zuul，目前很多项目中都是使用 Gateway 替代 Zuul。此外 Gateway 基于 Spring 5.x、Spring Boot 2.x 和 Project Reactor 构建，旨在提供一种简单而有效的方法来路由到 API，并为它们提供跨领域的关注点（安全性、监视/指标、限流等）；对于已经熟悉 Spring/Spring Boot 的开发人员很容易上手。
二、与 APISIX 的对比：APISIX 基于 OpenResty（Nginx+Lua）和 etcd 实现，与开发平台无关、无供应商锁定，可以从裸机运行到 Kubernetes，更适合常规 Ops 配置文件、以他们熟悉的包装提供产品（Kubernetes 的 Docker 映像和 Helm 图表），具有动态路由和热插件加载的特点，且支持多语言插件开发；而 Spring Cloud Gateway 更适合 Java 技术栈、与 Spring Cloud 生态（如 Nacos 服务发现、lb:// 负载均衡）无缝集成。选择哪个取决于技术栈与团队熟悉度。
三、Route 的组成：Route 称为路由，一个 Gateway 项目可以包含多个 Route。一个 Route 包含如下部分：
1. Route ID——自定的、路由的唯一标识；
2. predicates——路由断言，判断请求是否匹配和符合转发规则的要求，如果符合则转发到路由目的地；
3. URI——路由目的地，为一个地址，支持多种方式，包括 LB、http、websocket；
4. filters——路由过滤器，对请求或响应进行过滤处理，比如身份认证和权限校验、限流限速，此为可选项。
四、路由断言（RoutePredicateFactory）：断言是一个布尔函数，根据请求的不同属性（如路径、方法、头部等）来决定请求是否与路由匹配。Spring Cloud Gateway 包含许多内置的 Route Predicate Factories，所有这些断言都匹配 HTTP 请求的不同属性，多个断言可以通过逻辑与（and）结合起来一起使用。主要实现类包括 Datetime、请求的远端地址（RemoteAddr）、路由权重（Weight）、请求头（Header）、Host 地址、请求方法（Method）、请求路径（Path）和请求参数（Query）等类型。
五、过滤器机制：Gateway Filter 是网关中提供的一种过滤器，对路由的请求进行修改，可以对进入网关的请求和微服务返回的响应做处理。请求进入网关会碰到三类过滤器——当前路由的过滤器、DefaultFilter、GlobalFilter；请求路由后会将这三类过滤器合并到一个过滤器链集合中，排序后依次执行。每一个过滤器都必须指定一个 int 类型的 order 值，order 值越小优先级越高、执行顺序越靠前；GlobalFilter 通过实现 Ordered 接口或添加 @Order 注解指定 order 值，由用户自己指定；路由过滤器和 DefaultFilter 的 order 由 Spring 指定，默认按照声明顺序从 1 递增；当过滤器的 order 值一样时，会按照 DefaultFilter > 路由过滤器 > GlobalFilter 的顺序执行。当前支持 34 类路由过滤器工厂。
六、典型配置示例与 StripPrefix：
spring.cloud.gateway.routes:
- id: user-service（路由 id，自定义、必须唯一）
  uri: lb://userservice（lb 表示负载均衡，后面跟 Nacos 中微服务名称；也可用 http://127.0.0.1:8081 固定地址）
  predicates: - Path=/user/**（按路径匹配，以 /user/ 开头即符合要求）
  filters: - StripPrefix=1（转发前从请求路径中删除第一个前缀）
关于通配符：*（单星号）匹配一个路径段中的任意字符、不包括斜杠；**（双星号）匹配任意字符、包括多个路径段和斜杠。

**解析**

回答要点：优势部分抓“响应式(WebFlux)高性能 vs Zuul 阻塞式”、“Spring 自家维护替代 Zuul”、“与 Spring Cloud/Nacos 生态无缝集成”；Route 记“id + uri + predicates + filters”；断言与过滤器重点讲 order 值规则（越小越优先，相同时 DefaultFilter > 路由过滤器 > GlobalFilter）与 StripPrefix 的删除前缀语义。

### 98. 【面试·APISIX】Apache APISIX 相比传统 API 网关有哪些优势？其架构分为哪几个平面？

**答案**

一、APISIX 定位：Apache APISIX 是 Apache 软件基金会下的云原生 API 网关。它于 2019 年开源并由支流科技捐赠给 Apache 软件基金会，现已成为性能最高、社区最活跃的开源 API 网关项目；是中国唯一由初创公司贡献的 Apache 顶级项目，也是最快毕业（只用了 9 个月）的项目。
二、相比传统网关的优势：
1. 高性能：采用了基于 OpenResty 的架构以及高效的 Nginx 引擎，能够处理更高的并发请求、响应更快的 API——单核心 QPS 可达 1.5 万、延迟低于 0.7ms；
2. 配置实时生效：基于 ETCD 的事件驱动的配置生效时间小于 1ms，相对 Kong 轮询拉取需要 5s；从 NGINX 切换到 APISIX 不会降低性能，还能享受动态统一管理等特性带来的管理效率提升；
3. 不使用关系型数据库：APISIX 与其它 API 网关不同，使用 etcd 作为存储，让 APISIX 在底层上更加贴合云原生，也让它在系统高可用和性能上带来更多优势；
4. 全动态能力：支持热加载，不需要重启服务就可以更新 APISIX 的配置，避免了 Nginx 修改配置需重启对在线流量的影响；
5. 多平台支持：不但支持裸机运行，也支持在 Kubernetes 中使用，还支持与 AWS Lambda、Azure Function、Lua 函数和 Apache OpenWhisk 等云服务集成；
6. 精细化路由：支持使用 NGINX 内置变量做为路由的匹配条件，可自定义匹配函数来过滤请求、匹配路由；
7. 运维友好：支持与 Apache SkyWalking、Consul、Nacos、Eureka、HashiCorp Vault、Zipkin 等集成，通过 APISIX Dashboard 用友好直观的 UI 配置；
8. 多语言插件支持：支持多种开发语言进行插件开发，当前支持 80 多种插件，覆盖身份认证、安全、日志、可观测性等；
9. 部署更简单：提供 Docker 镜像、Kubernetes Helm Chart 等多种部署方式；
10. 丰富的流量管理功能：兼具动态、实时、高性能等特点，提供负载均衡、动态上游、灰度发布（金丝雀发布）、服务熔断、身份认证、可观测性等，可处理传统的南北向流量，也可以处理服务间的东西向流量。
三、架构的三个平面：APISIX 的架构主要分成两部分（并规划第三部分）：
1. 数据平面 Data Plane——真正处理来自客户端请求的组件，处理用户真实流量，包括身份验证、证书卸载、日志分析和可观测性等功能。数据面本身并不会存储任何数据，所以它是一个无状态结构；
2. 控制平面 Control Plane——增加独立的控制平面（CP），将来可以支持调度所有数据平面（DP），不局限于 APISIX。APISIX 在底层架构上和其它 API 网关的一个很大不同就在于控制面，APISIX 在控制面上选择使用 etcd；
3. AI 平面 AP——未来增加 AI 平面，因为仅是接入层本身没有价值，分析流动的数据并反哺业务才有价值。
四、其他能力：APISIX 支持作为 Kubernetes Ingress Controller 使用（支持全动态、无需重启加载，还支持原生 Kubernetes CRD）；也可以在服务网格 Service Mesh 中充当类似于 Envoy 这种 SideCar 的 Proxy 功能，替代 Envoy 处理服务间东西向流量；还可以支持 AI Agents。
五、应用场景：Load Balancer and API Gateway（传统 LB 与 API 网关）、Microservice Gateway（微服务网关，可平滑替换 Zuul、Spring Cloud Gateway、Dubbo 等）、Kubernetes Ingress、Service Mesh。

**解析**

回答要点：优势集中讲“OpenResty 高性能（单核 1.5 万 QPS、<0.7ms）、etcd 配置 <1ms 生效且不重启热加载、不用关系型数据库、80+ 插件、多平台与多语言”；架构平面记“数据平面（无状态）+ 控制平面（用 etcd）+ 规划的 AI 平面”。

### 99. 【面试·APISIX】APISIX 的核心概念 Route、Upstream、Service 之间的关系是什么？如何与 Nacos 集成实现服务发现？

**答案**

一、核心概念与关系：
1. Route（路由）：是 APISIX 中最基础和最核心的资源对象。APISIX 可以通过路由定义规则来匹配客户端请求，根据匹配结果加载并执行相应的插件，最后把请求转发给到指定的上游服务。路由中主要包含三部分内容：匹配规则、插件配置和上游信息。
2. Upstream（上游）：也称为上游，是对虚拟主机的抽象，即应用层服务或节点的抽象。上游的作用是按照配置规则对服务节点进行负载均衡，它的地址信息可以直接配置到路由或服务上。当多个路由或服务引用同一个上游时，可以通过创建上游对象、在路由或服务中使用上游 ID 的方式引用上游，减轻维护压力。
3. Service（服务）：是某类 API 的抽象（也可以理解为一组 Route 的抽象）。它通常与上游服务抽象是一一对应的，Route 与 Service 之间通常是 N:1 的关系。Service 用于定义 API 服务的通用属性，并将其与上游（upstream）关联，主要功能包括：①路由配置——service 可以通过路由规则（route）关联，指定哪些请求会被转发到该服务；②插件配置——可以在 service 层面上配置插件（如身份认证、限流、监控等），这些插件将应用于所有通过该服务的请求；③上游关联——service 会引用一个 upstream，定义具体的后端服务集群。
4. Admin API：用户可以通过 Admin API 控制 APISIX 实例（默认端口 9180）。
关系总结：Route 定义匹配规则与插件，并将请求转发到 Upstream；Service 是一组 Route 的抽象并引用 Upstream，Route 与 Service 通常是 N:1；Upstream 抽象后端服务节点并做负载均衡。多个 Route/Service 可复用同一个 Upstream。
二、与 Nacos 集成实现服务发现：
1. 背景：APISIX 内置支持的服务注册中心有 Nacos、etcd、Eureka 等，以及标准的 DNS 方式，可以平滑替换 Zuul、Spring Cloud Gateway、Dubbo 等微服务 API 网关；使用注册中心时，路由的 upstream 可通过服务发现方式获取节点。
2. 案例步骤（课件 8.6 案例）：①准备 Nacos 服务；②准备两个微服务生产者和消费者；③安装 APISIX 并配置使用 Nacos 注册中心（在 config.yaml 中配置 Nacos 的服务发现地址，如 hosts 与 8848 端口，并按需配置命名空间、分组与权重）；④APISIX 添加路由——方法 1：通过 Admin API 添加路由；方法 2：通过 APISIX Dashboard 添加路由（注意：先创建上游服务，Nacos 不能直接创建路由）；⑤通过 APISIX 网站进行测试访问。
3. 验证示例：curl -H "host: www.wang.org" 127.0.0.1:9080/echo/wangxiaochun 返回 Nacos Discovery Consumer Service Operation Result，说明 APISIX 已通过 Nacos 注册中心发现并转发到后端微服务。
4. 要点提醒：APISIX 默认 HTTP 数据面端口 9080、Admin API 端口 9180、HTTPS 端口 9443，etcd 默认 2379；APISIX Dashboard 默认 9000。

**解析**

回答要点：理清“Route（匹配+插件+转发）→ Upstream（后端节点+负载均衡）→ Service（一组 Route 的抽象，Route:Service 为 N:1）”；集成部分按“Nacos 注册微服务 → APISIX 配置 Nacos 服务发现 → 添加路由（Admin API 或 Dashboard，需先建上游）→ 通过 9080 验证”四步说明。
